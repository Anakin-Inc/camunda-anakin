# Camunda -- submission instructions

Real Camunda 8 Outbound Connectors (Java, Maven), targeting `api.anakin.io/v1`,
built against the real open-source [Camunda Connector
SDK](https://github.com/camunda/connectors) (`io.camunda.connector:*`). Covers
all 21 of Anakin's REST API capabilities as 21 separate connectors -- the
first 3 (`url-scraper`/`search`/`agentic-search`) from the original build
session, the remaining 18 added in a later session (see "Extension to all 21
capabilities" below).
Distinct from a marketplace/directory PR -- there is no central "submit your
connector" registry the way there is for, e.g., Dagster's
`community-integrations` repo. The deliverable here is the connector jar plus
its source and the 21 generated element templates, deployed into
whichever Connector Runtime a Camunda 8 operator already runs (self-managed
Docker image, or the Spring Boot connector-runtime starter).

## The sync-vs-poll design decision

The task brief asked specifically whether an Outbound Connector's
`execute()` is expected to block-and-poll internally for a long-running
external job, or whether Camunda's own retry/backoff mechanism
(`ConnectorRetryException` with a `backoffDuration`, re-invoking the job
later) is the documented pattern instead. Camunda's own docs page ("Use an
outbound connector") describes the retry/backoff mechanism's existence but,
when fetched directly, gives no explicit guidance on which pattern to use
for polling an external job -- so this was resolved from real,
currently-shipping connector source instead of docs prose:

**`camunda/connectors:connectors/aws/aws-textract`** -- a real, official,
currently-shipping Camunda connector that faces exactly this problem (AWS
Textract document analysis is an async, poll-for-completion AWS API) --
ships **three execution strategies** selectable per BPMN element
(`TextractConnectorFunction.execute` switches on
`request.getInput().executionType()`):

- `SYNC` -- direct synchronous AWS call.
- `POLLING` -- **blocks the job worker thread inside `execute()`**,
  `Failsafe.RetryPolicy` with a fixed delay (10 attempts x 1 minute default,
  ~9 minutes total), reading `PollingTextractCaller.java` directly.
- `ASYNC` -- fire-and-forget: submits the job, returns immediately with just
  the job ARN, leaving correlation to a separate later step in the BPMN
  process (e.g. an SNS notification driving an inbound connector/webhook).

Searching the whole `camunda/connectors` monorepo for
`ConnectorRetryExceptionBuilder` usage (`gh search code`) turned up **zero**
real connectors using it for "job not done yet, retry later" polling --
every hit is either the exception class itself or a generic-retryable-error
test fixture. `ConnectorRetryException` exists and is real, but it is not
the pattern the ecosystem actually uses for external-job polling; blocking
inside `execute()` (Textract's `POLLING` mode) is.

**This project follows the `POLLING` precedent**: `url-scraper` and
`agentic-search` both block inside `execute()`, polling the Anakin job
status endpoint every 2 seconds up to a 5-minute ceiling
(`AnakinApiClient.POLL_INTERVAL` / `POLL_TIMEOUT`) -- the same bounded
design this session's Appian plug-in used, scaled for Anakin's page-fetch/
AI-search jobs (seconds to low tens of seconds in normal operation) rather
than Textract's OCR jobs (which is why Textract's window is ~9 minutes and
this project's is 5). `search` needs no such decision -- it's genuinely
synchronous, one HTTP call, matching `Anakin.search` in `anakin-py`.

**Operational caveat, stated plainly**: blocking inside `execute()` means
the Zeebe job worker holds the job for up to `POLL_TIMEOUT`. The BPMN
service task / Connector Runtime's job-activation timeout must be configured
to exceed that, or Zeebe may reassign the job to a second worker mid-poll,
causing a duplicate Anakin job submission. This project does not configure
that timeout (it's an operator-side Connector Runtime / Zeebe client
setting, not something the connector jar controls) -- documented in
`AnakinApiClient`'s Javadoc and here, not silently assumed away.

## Re-verification pass (this session) -- two real, independently-caught defects

This directory's connector code, tests, `pom.xml`, README, and this file already
existed from an earlier work session. Per instructions, nothing below was
trusted at face value -- every claim was re-checked against the real Camunda
Connector SDK, `anakin-py`, and a fresh `mvn clean package` run. Two real
defects turned up, both fixed:

1. **`pom.xml` was not valid XML and `mvn` could not even read it.**
   Re-running `mvn clean package` fresh failed immediately at the POM-parsing
   stage: `Non-parseable POM ... in comment after two dashes (--) next
   character must be > not <space>`. The XML comment spec forbids the
   two-character sequence `--` anywhere inside a `<!-- -->` block except as
   the literal terminator immediately before `>` -- but this file's Maven
   comments used `--` freely as a stylistic em dash (e.g. `"...dependency
   graph -- see the dependency declaration below..."`), which is invalid XML,
   not just a Maven quirk. `target/` already contained a jar and surefire
   reports from an earlier build, meaning an earlier, differently-worded
   version of `pom.xml` did build successfully at some point, and the
   comments were later expanded to their current, more detailed prose without
   re-running `mvn` afterward to confirm the file still parsed -- so the
   previous "mvn clean package succeeds for real" claim in this file was
   stale/unverified at the time this session started. Fixed by replacing
   every mid-comment `--` with a real Unicode em dash (`—`) across all ten
   comment blocks in `pom.xml` (verified with `python3 -c "import
   xml.dom.minidom; xml.dom.minidom.parse('pom.xml')"` before touching
   Maven again). The `<description>` tag's own `--` usage was left untouched
   -- ordinary XML text content, not a comment, has no such restriction.
2. **`url-scraper`'s request body silently dropped a real, always-sent API
   parameter: `formats`.** Cross-checking `UrlScraperConnectorFunction`
   against `anakin-py/src/anakin/client.py`'s `Anakin.scrape()` and
   `blueprint-scribe-35/docs/SDK_API_CONTRACT.md` (the canonical shape
   reference) directly -- not from memory -- showed the real `POST
   /url-scraper` body always includes `formats` (`list[Literal["markdown",
   "html", "cleanedHtml", "json", "links", "images", "screenshot",
   "screenshotFullPage", "summary"]]`, default `["markdown"]`). The connector
   as found built its request body with `url`/`country`/`useBrowser`/
   `generateJson`/`forceFresh`/`sessionId`/`sessionName` only -- `formats`
   was never sent at all, a real fidelity gap against the ground-truth
   contract, not a stylistic choice documented anywhere. Fixed: added a
   `formats` field to `UrlScraperRequest` (`List<String>`, `@TemplateProperty`
   with `feel = FeelMode.optional` -- same binding style already used for
   `AgenticSearchRequest.schema`, since element-template-generator has no
   native multi-select widget for a `List<String>` and a FEEL list expression
   is the real pattern other Camunda connectors use for array inputs),
   defaulted to `List.of("markdown")` in `execute()` when omitted/empty
   (same "validate first, default after" pattern already used for
   `useBrowser`/`generateJson`/`forceFresh`), added `"formats"` to
   `@OutboundConnector.inputVariables`, and added a new regression test
   (`defaultFormatsIsMarkdownOnlyWhenOmitted`) asserting the wire body
   actually contains `"formats":["markdown"]` when the field is left blank.

After both fixes, `mvn clean package` was re-run clean from scratch and
genuinely succeeded -- see the "Verified, not assumed" section below, which
reflects this session's own build output, not the prior session's.

## Extension to all 21 capabilities (this session)

This directory originally covered 3 of Anakin's 21 REST API capabilities
(`scrape`/`url-scraper`, `search`, `agentic_search`). This session added the
remaining 18 as 18 more `OutboundConnectorFunction` classes + element
templates, following the exact conventions above (same package structure,
same `AnakinApiClient`-backed plumbing, same test pattern), so the directory
now covers all 21: `map`, `crawl`, `wire_discover`, `wire_catalog`,
`wire_read_action`, `wire_write_action`, `wire_identities`, `wire_login`,
`wire_build`, `monitor_create`, `monitor_list`, `monitor_changes`,
`monitor_control`, `ai_visibility_search`, `ai_visibility_sources`,
`session_list`, `session_delete`, `browser_task`.

**Ground truth for all 18**, read directly from Anakin's own MCP server
source (`anakin-mcp/src/client.ts` and `anakin-mcp/src/tools/*.ts`), not
guessed or inferred -- the same standard the original 3 connectors were held
to. Endpoint paths, HTTP verbs, request field names/defaults, and response
shapes (`job_id` vs `jobId` vs `id`, `search_id`, `workflow_id`, nested
`WireJobError { code, message, ... }` vs a flat error string, etc.) were all
cross-checked against that source before being written into Java.

### New shared plumbing added to `AnakinApiClient`

The original client only had `post`/`get`/`pollUntilTerminal` (fixed
`"completed"`/`"failed"` terminal states) -- not enough for the 18 new
endpoints' actual surface, so four real additions were made, each because a
specific new connector genuinely needed it, not speculatively:

- **`delete(String path)`** -- `session_delete` and `monitor_control`'s
  `delete` action are the only two endpoints in scope that use `DELETE`.
- **`withQuery(String path, Map<String,String> params)`** -- query-string
  builder mirroring `client.ts`'s own `withQuery` helper (same
  drop-if-empty-or-null semantics), needed by `wire_discover`,
  `wire_identities`, and `session_list`, which take optional filters as
  query params rather than a request body.
- **`encodePathSegment(String segment)`** -- path-segment URL-encoding
  (`URLEncoder` corrected from `+`-for-space form encoding to the
  path-correct `%20`) for slugs/ids interpolated into path templates
  (`wire/catalog/:slug`, `monitors/:id`, `sessions/:id`, `wire/jobs/:jobId`,
  `ai-visibility/search/:search_id`, `ai/jobs/:workflowId`) -- mirrors
  `encodeURIComponent` used throughout `client.ts` for the same purpose.
- **`pollUntilTerminal(path, timeout)` and `pollUntilTerminal(path, timeout,
  Predicate<Object> isTerminal)` overloads**, plus `"timed_out"` added to the
  default terminal-state set -- two real, distinct polling behaviors in the
  new endpoints that the original single-timeout/two-literal-status method
  couldn't express: (1) `browser_task`'s poll endpoint can report
  `"timed_out"` as a status distinct from `"failed"`, and the real API
  hard-caps a run at ~330s server-side, wider than the original 5-minute
  `POLL_TIMEOUT` default -- so a dedicated `BROWSER_TASK_POLL_TIMEOUT`
  (6 minutes) constant and timeout-parameterized overload were added; (2)
  `ai_visibility_search`'s poll endpoint is terminal on **any** status other
  than `"running"` (per `client.ts`: `if (search.status !== 'running')
  return search`), not a fixed `{"completed","failed"}` set, so a
  predicate-parameterized overload was added rather than special-casing a
  third literal value into the shared default.

### A real defect caught and fixed this session: reserved property id collision

Every element template the generator produces auto-injects standard
properties (`version`, **`id`** -- bound to `zeebe:taskHeader
elementTemplateId` -- `resultVariable`, `resultExpression`,
`errorExpression`, `retryCount`, `retryBackoff`) alongside the
`@TemplateProperty`-derived ones. The first draft of four new request
records (`MonitorListRequest`, `MonitorChangesRequest`,
`MonitorControlRequest`, `SessionDeleteRequest`) used a record component
literally named `id` for the monitor/session id being operated on -- the
natural, ground-truth-faithful name, since that is exactly what `client.ts`
calls it. Running `mvn package` failed for real:
`Failed to generate element templates: duplicate property id` -- the
generator derives each `@TemplateProperty`'s JSON property id from the Java
field name, so a field named `id` collided with the framework's own
reserved `"id": "id"` property. Fixed by renaming the four fields to
`monitorId` (three files) / `sessionId` (one file) -- the wire-format REST
paths (`/monitors/:id`, `/sessions/:id`) are unaffected, since those are
built by string concatenation inside each connector's `execute()`, not
derived from the Java field name. This is a real, previously-undocumented
constraint of `element-template-generator-maven-plugin` 8.9.6, caught by
actually running `mvn package` on all 18 new connectors, not discoverable
from the annotation Javadoc alone.

### Other design choices specific to the new connectors

- **`monitor_create` only sends fields the BPMN process actually set**,
  not the `@TemplateProperty` default values shown in Camunda Modeler for
  its ~20 optional fields -- matching `AnakinClient.monitorCreate`'s own
  "only send fields the caller set" behavior in `client.ts` (the API applies
  its own server-side defaults, e.g. `scope: "page"`, for anything omitted).
  This is a deliberate divergence from every other connector in this
  project (which do apply their own client-side defaults in `execute()`),
  documented in `MonitorCreateConnectorFunction`'s Javadoc so it doesn't
  read as an inconsistency.
- **`wire_read_action` / `wire_write_action`** are two separate connector
  classes with byte-for-byte identical request records
  (`WireReadActionRequest`/`WireWriteActionRequest`), mirroring the real MCP
  tool's own split (`wireReadActionTool`/`wireWriteActionTool` in
  `wire.ts`) -- its header comment explains why: a BPMN modeler picking an
  element should be visibly choosing a read (safe) vs. write
  (state-changing) action, not passing a hidden mode flag into one shared
  element. Both submit to the same `POST /wire/task` and poll the same
  `GET /wire/jobs/:jobId` only when the response carries a `job_id`
  (`AnakinApiClient.optionalJobId`, new) -- some Wire actions answer
  synchronously with terminal `data` inline.
- **Not reimplemented: the real MCP tool's `financialBlockReason` guard**
  (`anakin-mcp/src/tools/policy.ts`), which refuses `wire_write_action` /
  `wire_build` calls that look like a payment or fund transfer. That guard
  is Anthropic Connectors-Directory-specific policy layered on top of the
  REST API for an autonomous LLM agent loop, not part of the Anakin API
  contract this project wraps -- out of scope per the task brief's "ground
  truth is the REST API" framing, and noted here rather than silently
  dropped. Documented in `WireWriteActionConnectorFunction`'s Javadoc.
- **`wire_build`'s connector does not poll.** The real API returns
  `status: "pending"` from `POST /wire/build-request` and there is no
  documented `GET /wire/build-request/:id` in the ground-truth source given
  for this task (`client.ts`'s `wireBuild` doesn't poll either) -- so this
  connector's `execute()` returns the submit response directly, not
  invented as a polling loop against an endpoint that isn't confirmed to
  exist.

  under `zeebe:taskDefinition`, correct property groups
  (Authentication/Input/Session), correct `optional`/`constraints`/`feel`
  per field, matching the `@TemplateProperty` annotations they were
  generated from field-for-field.
- **`AnakinApiClientTest` (9 tests)** runs against a local
  `com.sun.net.httpserver.HttpServer` (built into the JDK, no live Anakin
  API key needed): POST/GET with the `X-API-Key` header, JSON success/error
  parsing, HTTP 4xx error mapping, malformed-JSON handling, the real
  `pollUntilTerminal()` loop reaching both `completed` and `failed`, and
  `jobId`/`job_id`/`id` key tolerance. Deliberately zero Connector SDK
  imports, same isolation rationale as the Appian build's equivalent class.
- **Three connector-level test classes (9 tests)** exercise
  `UrlScraperConnectorFunction`/`SearchConnectorFunction`/`AgenticSearchConnectorFunction.execute()`
  through the SDK's own real `OutboundConnectorContextBuilder` (not a mock
  of it) against the same local HTTP mock, injected via a
  `Function<String, AnakinApiClient>` constructor parameter -- the same
  dependency-injection-for-testability pattern real Camunda connectors use
  (`SendGridFunction(SendGridClientSupplier)`,
  `TextractConnectorFunction(clientSupplier, ...)`, confirmed from their
  real source). These exercise real `{{secrets.*}}` substitution, real
  Jakarta Bean Validation via `DefaultValidationProvider`, and the real
  submit-then-poll HTTP sequence end to end -- not just `AnakinApiClient` in
  isolation.
- **Two real, independently-caught defects, fixed during this build** (same
  rigor as the Appian plug-in's caught duplicate-scope bug):
  1. **Upstream dependency version conflict inside `connector-runtime-test`
     8.9.6's own transitive graph.** First attempt pinned
     `jackson-databind` to `2.22.0` (matching what `connector-object-mapper`
     resolves). Every connector-level test then failed with a real
     `java.util.ServiceConfigurationError` while `OutboundConnectorContextBuilder`
     built its internal FEEL/intrinsic-function machinery: `feel-engine`
     1.21.0's own transitive `jackson-module-scala:2.21.1` refuses to
     register against `jackson-databind >= 2.22.0` ("Scala module 2.21.1
     requires Jackson Databind version >= 2.21.0 and < 2.22.0"). Fixed by
     pinning `jackson-databind` to `2.21.4` instead -- a version already
     present elsewhere in that same dependency graph
     (`jackson-dataformat-yaml:2.21.4`, confirmed via `mvn dependency:tree`),
     not an arbitrary downgrade. This is a real inconsistency inside the
     SDK's own 8.9.6 test-scope dependency graph, caught by actually running
     the tests, not something invented for this write-up.
  2. **Wrong Bean Validation constraint on optional fields.** `useBrowser`,
     `generateJson`, and `forceFresh` were initially marked `@NotNull` on
     the theory that "the field always has a value once a default is
     applied" -- but `bindVariables()` runs Jakarta Bean Validation
     immediately on bind, before the connector's own code gets a chance to
     substitute a default for an omitted/null value. Every connector-level
     test omitting one of those fields failed with a real
     `jakarta.validation.ValidationException` (`ConnectorInputException`)
     from the SDK's own `DefaultValidationProvider`, not from anything in
     this project's own code. Fixed by dropping `@NotNull` from the three
     fields (they are genuinely optional; the default is applied in
     `execute()` after a successful, unconstrained bind).
  3. **`TemplateProperty.placeholder()` and `.language()` do not exist in
     the pinned 8.9.6 release.** Both were used in the first draft
     (`placeholder = "us"` on the country field, `language = "json"` on the
     agentic-search schema field) after being read off `TemplateProperty.java`
     fetched from the `main` branch -- which is ahead of the `8.9.6` tag.
     `mvn compile` failed with `cannot find symbol` for both, confirming the
     exact annotation surface actually shipped in `8.9.6` rather than the
     aspirational HEAD-of-main one. Both removed; the connectors still
     validate and default correctly without them.

## Not verified / not done

- **Never deployed to a real Camunda 8 Connector Runtime.** No access to a
  live Camunda 8 cluster or Connector Runtime in this sandbox -- never
  imported the generated element templates into a real Camunda Modeler,
  never confirmed the property panels (groups, conditions, secret-reference
  input) render as expected, never ran a real BPMN process with these
  service tasks against Zeebe.
- **Never called the real `api.anakin.io`.** No live API key available
  here. All tests exercise the same request/response code path against a
  local mock server instead; the real endpoint's actual behavior (rate
  limits, exact error payload shapes beyond the documented `{"error":
  "..."}`, actual job-completion latency for url-scraper/agentic-search) is
  unverified.
- **`engineVersion = "^8.9"` on all three `@ElementTemplate` annotations is
  an inference, not an independently confirmed compatibility figure.**
  Chosen to match the `8.9.x` Connector SDK line this project compiles
  against, mirroring the pattern real connectors use (`HttpJsonFunction`
  declares `engineVersion = "^8.10"` while depending on a version from that
  same release line) -- but no public Camunda-published
  SDK-version-to-engine-version compatibility matrix was found to verify
  this against directly, same category of caveat as the Appian plug-in's
  `application-version min` estimate.
- **`src/main/resources/icon.svg` is a generic placeholder** (a plain
  rounded-square monogram), not Anakin's real brand icon -- no real Anakin
  SVG/PNG asset was available in this sandbox. The connector-template-outbound
  repo's own real example ships a real brand SVG (Slack's, in that case)
  referenced the same way; this project's `icon = "icon.svg"` reference
  works and the file exists so the build succeeds and Camunda Modeler has
  something to render, but it should be swapped for a real Anakin asset
  before this ships publicly.
- **No integration test against a real Zeebe job worker / job-activation
  timeout.** The "operator must configure the job timeout to exceed
  `POLL_TIMEOUT`" caveat above is a documented design consequence, not
  something exercised end-to-end against a real Zeebe cluster's timeout
  behavior.

## Steps (needs a Camunda 8 environment + a live Anakin API key)

1. `mvn clean package` (already done here; reproducible).
2. Deploy `target/camunda-anakin-1.0.0.jar` into a Connector Runtime --
   either a custom image `FROM camunda/connectors-bundle` with this jar
   added, or a Spring Boot app on
   `io.camunda.connector:spring-boot-starter-camunda-connectors` with this
   jar on its classpath.
3. In Camunda Modeler, **Element Templates > Import element template ...**
   for each file under `element-templates/`.
4. Configure the `ANAKIN_API_KEY` secret in the Connector Runtime / Zeebe
   cluster's secret store with a real key from
   [anakin.io/dashboard](https://anakin.io/dashboard).
5. Add each of the 3 connectors to a test BPMN process as service tasks,
   reference `{{secrets.ANAKIN_API_KEY}}` in the Authentication field, and
   run them against the live `api.anakin.io` to confirm the response shapes
   match what `anakin-py`'s models predict, and that the job-activation
   timeout is configured wide enough for the polling connectors.
